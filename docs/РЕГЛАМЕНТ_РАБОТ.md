Да. Теперь нужен уже не архитектурный документ, а **план производства и проверки**, где каждая новая часть появляется только после того, как предыдущая доказала свою работоспособность.

Я бы сделал его именно как отдельный документ/промпт для LLM. Важная мысль: `v_01`, `v_02` и т. д. должны означать **тестовые сборки с зафиксированным результатом**, а не просто номера версий файлов.

Современная база здесь — Manifest V3 и актуальные Edge/Chromium Extension APIs; Microsoft прямо указывает MV3 как текущую модель, а локальная установка для тестирования официально поддерживается Edge. ([Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/manifest-v3?utm_source=chatgpt.com "Overview and timelines for migrating to Manifest V3 - Microsoft Edge Developer documentation | Microsoft Learn")) Для E2E-тестирования расширений существуют Puppeteer/Playwright, но я бы **не вводил их с первого шага**: сначала ручная проверка каждого вертикального модуля в реальном Edge, затем автоматизация тех проверок, которые действительно стабилизировались. ([Chrome for Developers](https://developer.chrome.com/docs/extensions/how-to/test/end-to-end-testing?utm_source=chatgpt.com "End-to-end testing for Chrome Extensions  |  Chrome for Developers"))

# 1\. Главный принцип организации работ

## Один модуль → одна тестовая сборка → один проверяемый результат

Не допускается:

```
написали 7 модулей
        ↓
собрали всё
        ↓
пытаемся понять, что сломалось

```

Работа ведётся так:

```
МОДУЛЬ
   ↓
реализация
   ↓
сборка v_XX
   ↓
загрузка в Edge
   ↓
тест
   ↓
отчёт
   ↓
PASS / FAIL
   ↓
только после PASS следующий модуль

```

# 2\. Что такое `v_01`, `v_02`...

Это **контрольные тестовые сборки**.

Например:

```
v_01

```

не означает:

> «первая версия всего расширения».

Это означает:

> **состояние проекта после завершения конкретного этапа, которое можно загрузить в Edge и повторно проверить.**

Каждая сборка должна быть воспроизводима.

Например:

```
reports/
    v_01/
        BUILD.md
        TEST.md
        RESULT.md

    v_02/
        BUILD.md
        TEST.md
        RESULT.md

```

---

# 3\. Не смешивать три вида тестирования

Каждый модуль проверяется на трёх уровнях.

### Уровень A — технический

Работает ли сам код?

```
syntax
imports
messages
storage
API

```

### Уровень B — интеграционный

Правильно ли модуль взаимодействует с соседним модулем?

```
content.js
    ↓
adapter
    ↓
normalizer

```

### Уровень C — пользовательский

Получается ли требуемое действие в реальном VK.RU?

```
пользователь
    ↓
VK.RU
    ↓
расширение
    ↓
результат

```

**PASS на уровне A не означает PASS всего модуля.**

# 4\. Этап 0 — контрольный каркас

### Цель

Получить минимальное расширение, которое:

1. имеет корректный `manifest.json`;

2. загружается в Edge;

4. background/service worker запускается, если он предусмотрен архитектурой;

5. между компонентами можно диагностически обменяться сообщением.

→ проект

```
PASS:
расширение загружено
VK.RU открыт
content script работает
ошибок manifest/runtime нет

```

### Если FAIL

Следующий модуль **не начинать**.

# 19\. Автоматизация тестов — не с первого дня

Я бы специально записал это в регламенте.

Не надо сразу устанавливать:

```
Playwright
Puppeteer
Jest
Vitest
Selenium

```

только потому, что они существуют.

Сначала нужно выяснить, **что вообще стабильно тестируется**.

Для расширений Chromium/Edge E2E-автоматизация через Puppeteer/Playwright является нормальным современным направлением. Официальная документация Chrome прямо указывает Puppeteer/Playwright среди поддерживаемых подходов к E2E-тестированию расширений. ([Chrome for Developers](https://developer.chrome.com/docs/extensions/how-to/test/end-to-end-testing?utm_source=chatgpt.com "End-to-end testing for Chrome Extensions  |  Chrome for Developers"))

Но в вашем проекте я бы сделал так:

```
v_01–v_05
    ↓
ручное Edge DevTools тестирование

v_06–v_10
    ↓
ручное + подготовка автоматизируемых сценариев

после стабилизации
    ↓
Playwright/Puppeteer

```

Иными словами:

> **автоматизировать уже понятный тест, а не автоматизировать исследовательскую неопределённость.**

```

     ↓

     ↓

```

 ↓

# 22\. Категории результата

Каждый тест заканчивается одним из четырёх статусов:

```
PASS
FAIL
BLOCKED
NOT TESTED

```

Особенно важен:

### BLOCKED

Например:

> VK.RU изменил поведение страницы, невозможно подтвердить гипотезу.

Это **не повод писать костыль**.

---

# 23\. Что запрещено LLM во время работы

LLM не имеет права самостоятельно:

* переходить к следующему модулю после FAIL;

* менять архитектуру без отдельного решения;

* добавлять библиотеку «для удобства»;

* вводить React-зависимость без доказанной необходимости;

* заменять navigation target CSS-селекторами без обоснования;

* переносить старую логику только потому, что она существует;

* добавлять поддержку других порталов;

* оптимизировать мобильную версию;

* выполнять несколько незапрошенных шагов за один ответ.

## Главное отличие этого проекта от старого

Старый проект развивался примерно:

```
функциональность
 ↓
ещё функциональность
 ↓
ещё база
 ↓
ещё обработчики
 ↓
универсальность

```

Новый проект:

```
доказательство
 ↓
модуль
 ↓
тестовая сборка
 ↓
PASS
 ↓
следующее доказательство

```

И только после прохождения всей цепочки:

```
VK.RU
 ↓
сущность
 ↓
navigation target
 ↓
контекст
 ↓
собственный слой
 ↓
действие пользователя
 ↓
сохранение

```

мы получаем основание для дальнейшего развития.

**Именно это я бы сделал центральным смыслом `РЕГЛАМЕНТ_РАБОТ.md`: не «план написания кода», а управляемая последовательность доказательств работоспособности каждого слоя.**

Для Edge это особенно уместно: MV3 уже является текущей моделью, а `contextMenus`, content scripts и service worker относятся к поддерживаемой современной архитектуре расширений.

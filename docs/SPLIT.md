# SPLIT.md — регламент раздвоения: общее ядро + две ветви

## 0. Смысл и границы ветвей
- context-vkru — личная «вторая память»: живые персоны/сообщества;
  ▲-метки, «грязь» (блеклость+запрет), персоны (SIM), группы,
  экспорт MPE/Google.
- mem-2026 — «Восстановление связей»: бойцы братского кладбища
  (3310, из них 3251 неизвестный; obd-memorial.ru, приказ №181);
  поля документа «кого известить» / «адрес»; цель — нить
  солдат → живой потомок; экспорт в «Мост поколений».
  mem-2026 — рабочее имя мемориальной ветви, НЕ закрепляется
  (временная адаптация стороннего проекта).
- Ветвь в VK/OK: точечная фиксация собеседников, статусы переговоров,
  выявление «которые могут быть причастны» (потенциальные
  потомки/родственники) — поверх общего ядра.

## 1. СУТЬ
context-vkru («вторая память») и mem-2026 («Восстановление Памяти») —
два продукта на ОБЩЕМ ядре. Ядро = код + регламенты; ветви = цели,
данные, сценарии.

## 2. Общее ядро (донор — context-vkru)
normalize.js (порталы vk/ok/dzen, id, reply), storage.js (карточка v3),
messaging.js, изъятие (ПКМ → CAPTURED), маркировка (scan/wrap/ctx-*),
регламенты (стиль AGENTS/INSTRUCTION/HANDOVER).

## 3. Точка раздвоения
PASS v07f + завершение v_08r (слияние/каноникализация).
Раньше — тащим незавершённое ядро и дублируем фиксы;
позже — ветви обрастают чужими фичами.
Причина: «может быть причастен» = один человек под разными никами
VK/OK (нужно слияние); затем экспорт живой карточки (v_09r).
До точки: mem-2026 отдельно не развивать, третьего репо не создавать.

## 4. Собственный слой данных mem-2026 (НЕ тащить в context-vkru)
- soldier: {имя, место, даты, source: obd-memorial,
  реквизиты: фонд/опись/дело/страница, notify: имя, address: строка}.
- descendant: живая карточка v3 + «может быть причастен»
  (гипотеза/подтверждено/отклонено) + evidence (ссылки, документ).
- связь: soldier ↔ descendant; evidence = документ + ссылка.
- Коммит = клеймо: «проверено; лежит здесь; эта мать ждала его».
  Репо-гейт (raw-верификация проектировщиком) — в обеих ветвях.

### Дополнения модели данных
- soldier.plate: "none | documented | approved | engraved";
- descendant.track: "volunteer | junior | school";
- connection.mentor: кто верифицировал (старший/джуниор).

## 5. УЗКАЯ ЗАДАЧА («персоны, которые могут быть причастны»)
Карточка мемориальной ветви = наш контракт v3 + поля:
причастность (гипотеза/подтверждено/отклонено),
evidence (ссылки = наш metUrl), связи (с кем в переписке —
«восстанавливаем разорванное»). Статусы активного/архива/
блока = наш status+visual.faded.

## 6. Пересечение ветвей — ТОЛЬКО через данные
Живая персона мемориальной ветви с меткой «может быть причастен» →
экспорт vCard 3.0 / CSV (R5) → mem-2026 → «Мост поколений».
context-vkru в мемориальном контуре не участвует; базы не смешиваются
(разные ключи storage, профили, репо).

## 7. Данные не смешиваются никогда
Раздельные базы (разные ключи storage/профили), раздельные метки
(▲ память / ⚑ переговоры), раздельные экспорты.

## 8. Треки mem-2026
А «ПЛИТЫ»: 600+ персон с документальным подтверждением
  захоронения на мемориале «Копечь». Статус персоны:
  documented → approved (проект плит согласован) → engraved.
  Экспорт списков на изготовление (CSV/печать).
Б «ПОИСК»: остальные неустановленные — работа с волонтёрами;
  «могут быть причастны» = потомки/родственники; изъятие в
  соцсетях (VK/OK) — поверх общего ядра.
С «ПЕРЕДАЧА»: проект уходит в школу с музеем памяти;
  джуниоры ищут контакты через соцсети. Отсюда требования:
  низкий порог входа (простые статусы, регламент-памятка,
  экспорт), наставничество (коммит джуниора верифицирует
  старший — клеймо доказательства).

## 9. Этический контур («техника бережная, как смысл»)
- Массового сбора НЕТ: только точечное изъятие (Решение №2).
- Живые: никакой публикации/экспорта без решения пользователя;
  «грязь»/запреты — только личная ветвь.
- Данные бойца: источник + реквизиты + автор коммита обязательны.
- В мемориальном контуре нет сторонних сервисов, кроме целевого
  экспорта («Мост поколений»).

## 10. Механика раздвоения (SPLIT-0)
1. docs/CORE.md — состав ядра и происхождение.
2. Копия файлов ядра в репо мемориальной ветви коммитом
   chore(core): sync core from context-vkru @<hash>. Без сабмодулей.
3. Фиксы ядра — только у донора; в ветвь — одним sync-коммитом.
4. OK: core-шаг K-OK (адаптер id ok.ru) после SPLIT-0 — обе ветви
   получают бесплатно.
5. Регламенты копируются один раз в момент раздвоения.

## 11. Минимум движений
Третьего репо нет; чужих полей в своей ветви нет; ядро в двух местах
одновременно не правится; узкая задача («выявление причастных») —
только в mem-2026, поверх общего ядра.

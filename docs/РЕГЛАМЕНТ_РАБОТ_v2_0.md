## ЧАСТЬ 1. КОНТЕКСТ ПРОЕКТА (PRODUCT VISION)
Этот раздел обязателен к прочтению LLM перед началом любой работы. Он описывает ЧТО мы строим и КАКУЮ философию исповедуем.

### 1.1. Назначение
Проект представляет собой браузерное расширение (Manifest V3) для Microsoft Edge (Desktop), предназначенное для **точечного взаимодействия** пользователя с сущностями (персоны, сообщества, авторы комментариев) на портале `https://vk.ru/`.
Это **НЕ** система массового сбора данных, **НЕ** CRM и **НЕ** автоматический парсер. Это инструмент для ручного добавления заметок, маркеров и статусов к конкретным объектам, которые интересуют пользователя.

### 1.2. Архитектурная философия (КРИТИЧЕСКИ ВАЖНО)
1. **Принцип "Собственного слоя":** Расширение **НЕ** модифицирует внутреннюю логику VK.RU, **НЕ** вмешивается в React-компоненты и **НЕ** ломает штатный UI VK. Оно создает *собственный UI-слой* (DOM-маркеры, CSS-классы) поверх существующего интерфейса.
2. **Идентификация через Navigation Target:** Первичный и единственный надежный источник идентификации — это URL ссылки (`href`) на сущность. Хрупкие CSS-классы верстки (например, `vkit-XXXX`, `Post__author`) считаются **OBSERVED** (наблюдаемыми) и **ЗАПРЕЩЕНЫ** для использования в качестве первичных ключей.
3. **Отказ от Legacy:** Старый код проекта (8-10 летней давности) рассматривается только как источник идей. Никакие старые функции, диспетчеры (`Handlers = new Map()`) или глобальные базы данных не переносятся автоматически.

- **Браузер:** Microsoft Edge (Desktop)
- **Портал:** Только `https://vk.ru/` (поддержка vk.com, мобильных версий и других порталов **ЗАПРЕЩЕНА**).

- **Foreground:** Content Scripts (`content.js`).

- **ЗАПРЕЩЕНО:** Использование React, Vue, jQuery, Tailwind, Bootstrap или любых иных внешних библиотек/фреймворков. Весь код пишется на Vanilla JS (ES6+).

## ЧАСТЬ 3. КОНТРАКТ ДАННЫХ (ENTITY CONTRACT)

Все компоненты системы обмениваются данными в формате стандартизированного объекта `ENTITY`. LLM не имеет права изменять эту структуру без согласования.

```javascript
// ENTITY CONTRACT
{
    type: "PERSON" | "COMMUNITY" | "COMMENT_AUTHOR" | "POST_AUTHOR",
    identity: {
        id: "string",       // Устойчивый ID (извлечен из URL, например "id123")
        url: "string",      // Нормализованный Navigation Target (без GET-параметров)
    },
    context: {
        source: "comment" | "post" | "sidebar",
        parentPostId: "string | null",
        threadId: "string | null"
    },
    sourceElement: HTMLElement, // Ссылка на DOM-узел (только для content.js, не сериализуется)
    capabilities: { canTag: true, canNote: true }
}
```

## ЧАСТЬ 4. ГЛАВНЫЙ ПРИНЦИП ОРГАНИЗАЦИИ РАБОТ

**Один модуль → одна тестовая сборка → один проверяемый результат.**

Работа ведется строго последовательно:

1. LLM реализует модуль.
2. Собирается версия `v_XX`.
3. Пользователь загружает в Edge и тестирует.
4. Фиксируется отчет в `reports/v_XX/` (`BUILD.md`, `TEST.md`, `RESULT.md`).
5. **Только после статуса PASS** начинается работа над следующим этапом.

При статусе **FAIL** или **BLOCKED** работа возвращается внутрь текущего модуля. Перескакивать через этапы или менять архитектуру "на ходу" **ЗАПРЕЩЕНО**.

---

## ЧАСТЬ 5. ЖЕСТКИЕ ПРАВИЛА ДЛЯ LLM (ОГРАНИЧЕНИЯ)

LLM не имеет права самостоятельно:

1. Переходить к следующему модулю после FAIL.
2. Менять архитектуру без отдельного решения Пользователя.
3. Добавлять внешние библиотеки (npm-пакеты) "для удобства".
4. Заменять `navigation target` (href) на CSS-селекторы без железного обоснования.
5. Переносить старую логику (Legacy) только потому, что она существовала.
6. **Галлюцинировать результаты тестов.** LLM не имеет доступа к браузеру. LLM только генерирует код и пишет инструкцию по тестированию (`TEST.md`). Факт PASS/FAIL устанавливает исключительно Пользователь.
7. **Писать адаптер вслепую.** При разработке `vkru.js` (Этапы 2-4), LLM обязана предоставлять Пользователю **диагностический snippet** (скрипт для консоли DevTools), чтобы Пользователь мог вручную проверить гипотезы о структуре DOM (наличие `data-*` атрибутов, структуру ссылок) на реальной странице [VK.RU](http://VK.RU).

## ЧАСТЬ 6. ЭТАПЫ ПРОИЗВОДСТВА (v_01 — v_15)

*(Здесь остается ваш список этапов, но с уточнениями для LLM)*

- **Этап 0 (v_01): Контрольный каркас.** Минимальный MV3 манифест, загрузка в Edge, запуск `content.js` на `vk.ru`.
- **Этап 1 (v_02): Диагностический канал.** Обмен сообщениями (PING/PONG) между `content.js` и `background.js` (Service Worker).
- **Этап 2 (v_03): **[**VK.RU**](http://VK.RU)** Adapter (Обнаружение).** Поиск `sourceElement` в DOM. *Требует диагностических скриптов для консоли.*
- **Этап 3 (v_04): Navigation Target.** Извлечение и нормализация URL из `href`. Отбрасывание трекеров.
- **Этап 4 (v_05): Нормализатор.** Формирование объекта `ENTITY` по контракту.
- **Этап 5 (v_06): Контекст.** Привязка сущности к родителю (пост, тред).
- **Этап 6 (v_07): Собственный визуальный слой.** Инъекция диагностического маркера `[ENTITY]` через `styles.css`. Проверка изоляции стилей.
- **Этап 7 (v_08): Треугольник.** Замена маркера на `▲`. Проверка реакции на динамическую перерисовку DOM (SPA-навигация).
- **Этап 8 (v_09): Действие по треугольнику.** Клик по маркеру -\> открытие `dialog.html`.
- **Этап 9 (v_10): ПКМ / Выделение.** Интеграция с `chrome.contextMenus`.
- **Этап 10 (v_11): Сохранение.** Запись в `chrome.storage.local`. Проверка персистентности.
- **Этап 11-14 (v_12 - v_15):** Маркеры, примечания, календарь, финальная интеграция.

## 💡 Мои предложения и пояснения к правкам

1. **Добавлен раздел "Диагностика" (Правило 7 и Этапы 2-4):**
   Это **самое важное процессуальное изменение**. LLM физически не может видеть DOM сайта `vk.ru`. Если она просто напишет `document.querySelector('.vkit-ewZ0L2')`, это будет галлюцинация, которая сломается через неделю.
   *Решение:* LLM обязана выдавать вам **bookmarklet или snippet для консоли** (например: *"Запустите этот код на странице комментария и скопируйте мне вывод, чтобы подтвердить, что у автора есть `data-author-id`"*). Это превращает разработку адаптера из гадания в научный метод.

2. **Явный запрет на фреймворки (Правило 2.2):**
   В старом коде была куча зависимостей. LLM по умолчанию любит предлагать React или хотя бы jQuery. Для расширения, которое просто рисует треугольник поверх чужого сайта, Vanilla JS + MV3 API — это золотой стандарт. Запрет прописан явно.

3. **Изоляция стилей (Этап 6):**
   Добавлено требование проверять изоляцию стилей. Если ваш `styles.css` использует общие селекторы (например, `a { color: red; }`), вы покрасите весь сайт VK. Стили расширения должны быть жестко привязаны к специфичным классам (например, `.ctx-marker-triangle`).

4. **Четкий контракт `ENTITY`:**
   LLM теперь не будет каждый раз придумывать новую структуру объекта для передачи между `content.js` и `background.js`. Контракт зафиксирован в документе.

5. **Запрет на галлюцинации тестов (Правило 6):**
   LLM часто любят писать: *"Я проверил, код работает, PASS"*. Это опасно. В регламенте жестко прописано, что **статус PASS выдает только человек** после ручной проверки в Edge.
